# 全局工程规范

适用于各类项目和技术栈的软件开发、维护、测试与交付。

## 始终遵守

- 遵守平台权限和适用的项目指令。在已确认的目标和授权范围内工作，保留无关改动和有价值的记录。
- 根据任务检查相关源码、项目文档、配置、测试和 Git 状态。对照实际实现核实重要说法。
- 对简单、低风险的改动，检查相关代码，完成所需修改，执行针对性检查并汇报结果。任务或项目有更高要求时，采用相应流程。
- 变更已确认的需求或验收标准，进行重大架构变更、显著改变核心技术选型或公开兼容性约定，或执行不可逆、高风险操作前，必须取得用户确认。合并 PR、正式发布及部署到生产环境必须获得明确授权。
- 确认完成前须核验实际交付物，并报告未解决的失败和尚未验证的事项。正式任务由主 Agent 负责最终验收。

## 随任务进展选择章节

在作出相关决定或采取相关行动前，读取所有命中触发条件的章节。一项任务可以命中多章。已读且仍在当前任务上下文中的章节可以直接沿用。实施中出现新的触发条件时，先读取对应章节，再继续受影响的工作。

若无法读取必读章节，说明缺失的是哪一章，并暂停受影响的决定或操作。其他独立工作在安全的前提下可继续。各章包含完整条款及适用条件。

| 何时读取 | 章节 |
| --- | --- |
| 需要判断规则、任务范围或授权，包括处理冲突与例外。 | [01. 适用范围与核心原则](chapters/01-scope-and-core-principles.md) |
| 进入陌生项目，调查文档与实现的重大差异，或创建、更新、归档工程文档。 | [02. 项目理解与文档管理](chapters/02-project-understanding-and-documentation.md) |
| 分析有实质影响的实现变更，解决影响实施的歧义，或拟变更已确认的需求、验收标准、核心技术选型或兼容性承诺。 | [03. 需求分析与用户沟通](chapters/03-requirement-analysis-and-user-interaction.md) |
| 规划有实质依赖的工作，创建或更新正式任务，协调集成，或移交未完成的工作。 | [04. 工程流程与任务管理](chapters/04-engineering-workflow-and-task-management.md) |
| 委派任务、协调并行工作，或为重要功能、核心架构变更或高风险工作安排独立评审。 | [05. 多 Agent 协作](chapters/05-multi-agent-collaboration.md) |
| 创建、切换或清理分支或 Worktree，提交改动，处理 PR 或 CI，或修改仓库保护设置。查看常规 Git 状态和差异时可直接检查。 | [06. Git、PR 与 CI](chapters/06-git-pr-and-ci.md) |
| 设计或变更模块职责、依赖关系、共享或公开接口、系统架构，或处理架构决策记录（ADR）。 | [07. 架构与决策管理](chapters/07-architecture-and-decision-management.md) |
| 诊断有实质影响的失败，处理反复失败或需要上报的问题，或执行正式验收与交付。 | [08. 故障处理与交付](chapters/08-failure-handling-and-delivery.md) |

例如，熟悉项目中的文案修复可直接按上述规则完成。处理 PR 的 CI 失败需读第 06 和 08 章。若修复涉及已确认的公开接口变更，还需在提出变更前读第 03 和 07 章。

章节链接以本索引所在目录为基准。章节中的 `docs/task.md` 等路径指向当前工作项目。需要操作步骤或文档格式时，查阅工程规范仓库中的指南和模板。
