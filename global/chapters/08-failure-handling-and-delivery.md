# 08. 故障处理与交付

## 8.1 发现与分类

- 必须对有实质影响的失败进行分类。
- 应用修复前，必须调查根本原因。
- 必须确定受影响的任务、模块和 Worker。
- 必须区分已确认的原因与假设。
- 必须保留相关日志和证据。
- 不得隐瞒未解决的失败。

失败类别包括以下各项。

- ENVIRONMENT（环境）
- IMPLEMENTATION（实现）
- TEST（测试）
- INTEGRATION（集成）
- ARCHITECTURE（架构）
- SECURITY / DATA（安全或数据）

## 8.2 局部故障隔离

- 必须确定失败的影响范围。
- 必须暂停受影响的任务及依赖这些任务的操作。
- 安全时，必须允许无关任务继续执行。
- 影响共享资源、接口、安全或数据完整性时，可以扩大暂停范围。
- 恢复任务前，必须重新评估依赖。

## 8.3 恢复与重试

- 应由原 Worker 修复自己的工作。
- 必须保留现有工作和相关提交。
- 必须按失败类型设置适当的重试上限。
- 实现、测试或 CI 反复失败时，默认最多自动进行两次有实质内容的修复尝试。
- 简单环境问题在可安全处理时，可以自主解决。
- 架构方面的失败必须触发重新分析。
- 出现安全或数据完整性风险时，必须立即停止受影响的操作。
- 达到适用的重试上限后，必须停止重复修复。
- 必须重新评估实施策略。
- 替换或重新分派 Worker 时，必须提供足够的背景。
- 清理前必须检查 Worktree 状态。
- 不得丢弃未经验证的工作。

Reviewer 要求的改动应由原 Worker 处理，无需机械套用通常的两次尝试上限。

## 8.4 上报与用户通知

发生以下情况时，Agent 必须通知用户。

- 已确认的需求存在重大冲突。
- 必须进行重要架构变更。
- 发现严重的安全或数据完整性风险。
- 需要执行不可逆操作。
- 任务超出当前授权。
- 在已确认的范围内无法可靠完成任务。

通知必须说明以下内容。

- 发现的问题。
- 可能的原因。
- 受影响的任务、模块和组件。
- 调查结果。
- 建议方案及其取舍。
- 需要用户作出的决定。

## 8.5 开发记录

- 应保留重要的开发报告。
- 应保留有价值的测试证据。
- 不得伪造测试或评审结果。
- 不得随意删除历史证据。
- 适当时应归档过时的历史资料。

重要开发记录存放在 dev/records/。

大型生成产物应保留在 artifacts/，默认不应提交。

## 8.6 最终交付与验收

主 Agent 必须在验收正式任务前核验实际交付物。

相关验证可以包括以下内容。

- 是否满足需求。
- 自动化测试结果。
- 构建结果。
- 必需的 PR 评审。
- 集成验证。
- 文档一致性。

最终报告应保持结构一致，详细程度与任务复杂度相称。

报告应包含以下内容。

- 已完成的工作。
- 重要改动。
- 实现摘要。
- 验证结果。
- 评审及 PR 状态。
- 剩余风险和限制。
- 已更新的文档。

主 Agent 不得在未核验实际结果时宣称成功。

合并 PR、正式发布和部署到生产环境必须取得用户明确授权。
