# 04. 工程流程与任务管理

## 4.1 选择工作流程

必须根据任务的复杂度、范围、依赖和风险选择合适的流程。

常见执行方式如下。

**直接执行**

适用于简单改动。

- 理解问题。
- 检查相关代码。
- 实施改动。
- 运行适当的检查。
- 汇报结果。

**按计划执行**

适用于中等规模的改动。

- 分析需求和架构。
- 制定实施计划。
- 确定依赖关系。
- 实施并测试。
- 评审并验证结果。

**完整工程流程**

适用于复杂项目和重大改动。

- 需求分析。
- 技术调研。
- 架构设计。
- 任务规划。
- Agent 协调。
- 实施与测试。
- CI 和 PR。
- 评审与集成。
- 最终验收与交付。

应灵活选择执行方式，无需为项目或任务设定固定等级。

不得要求所有任务都走完整工程流程。

不得仅为节省时间而跳过必要的分析或验证。

## 4.2 任务规划

主 Agent 负责制定正式开发计划。

- 必须明确开发目标。
- 必须确定相关需求。
- 必须识别有实质影响的任务依赖。
- 应按独立目标、交付物和执行依赖拆分任务。
- 不得将任务无谓地拆到单个函数、文件或琐碎操作。
- 不得仅为提高 Agent 并行利用率而创建正式任务。

Worker 的内部子任务由主 Agent 管理，无需列入 docs/task.md。

## 4.3 任务管理

docs/task.md 由主 Agent 独自负责和维护。

任务编号采用以下格式。

`YYYYMMDD-HHmm-NNN`

示例编号如下。

- 20261123-1430-000
- 20261123-1430-001
- 20261123-1615-000

编号和维护须遵守以下规则。

- 使用项目所在时区。
- 在同一批任务创建时分配序号。
- 任务编号只需在当前任务清单内唯一。
- 历史记录必须使用完整的任务编号和名称。
- 同一项目同一时刻应只有一个主 Agent 独立维护正式任务清单。
- 并行会话必须协调任务分配和对 task.md 的修改。

可用的任务状态如下。

- READY 表示任务可执行。
- WORKING 表示任务正在执行。
- WAITING 表示在等待依赖、确认、外部条件或问题解决。
- FINISH 表示主 Agent 已验收。

可用的优先级如下。

- HIGH
- MEDIUM
- LOW

状态管理须遵守以下规则。

- 必须写明进入 WAITING 的原因。
- 不得允许 Worker 直接修改 task.md。
- 不得仅凭 Worker 的完成消息将任务标为 FINISH。
- 完成最终验证并更新必要记录后，必须将已验收的任务从 task.md 移除。

## 4.4 依赖管理

- 必须识别有实质影响的任务依赖。
- 有收益时，应并行执行互相独立的任务。
- 前置条件未满足时，不得执行依赖这些条件的任务。
- 必须以 docs/task.md 为正式任务依赖的权威记录。
- 可以自动生成依赖关系图。
- 发生失败或架构变更后，必须重新评估受影响的依赖。
- 必须将故障隔离在受影响范围内，避免无谓地停止无关任务。

恢复 WAITING 任务前，主 Agent 必须确认阻塞条件已解除。

## 4.5 任务验收与移交

- 验收前必须核验实际交付物。
- 涉及多个任务或模块时，必须进行集成验证。
- 将任务标为 FINISH 前，必须完成适用的评审和检查。
- 改动实施后，必须更新相关文档。
- 应保留有价值的开发记录和证据。
- 将未完成的工作移交给其他 Agent 时，必须提供足够的背景。

PR 获批后，关联的正式任务仍须按验收条件核验。

将任务标为 FINISH 前，主 Agent 必须确认所有必要改动均已集成。

等待用户授权合并期间，任务必须保持 WAITING。

主 Agent 负责最终验收和维护 task.md。
