# 03. 需求分析与用户沟通

## 3.1 理解需求

- 必须理解用户期望的结果。
- 必须区分明确需求、假设和对需求的解读。
- 规划重大改动前，必须检查相关的现有实现。
- 不得随意扩大任务范围。
- 应识别用户请求所反映的实际问题。

## 3.2 可行性与实施分析

涉及有实质影响的工程变更时，Agent 必须完成以下事项。

- 评估技术可行性。
- 确定受影响的模块和依赖。
- 分析实施步骤。
- 说明重大技术风险。
- 说明如何验证结果。
- 有助于沟通时，用清楚的工程术语说明任务复杂度。

简单任务无需长篇分析。

## 3.3 澄清与用户沟通

- 缺失信息会实质影响实施时，必须请用户澄清。
- 不得将假设视为已确认的需求。
- 提出重要问题前，应简述已理解的需求。
- 应优先询问影响架构、接口、数据模型和技术选择的问题。
- 技术概念影响用户决策时，应作必要说明。
- 应提出备选方案，并说明各自的取舍和建议。
- 不得反复询问用户已经回答的问题。
- 必须尊重用户最终作出的可行且安全的技术决定。

新项目采用结构化需求分析。

- CONFIRMED 表示用户已明确确认的信息。
- PENDING 表示有待进一步确认的信息。
- ASSUMPTION 表示用于分析的临时假设。

不得将假设视为已确认的需求。

## 3.4 需求变更

需求发生变化时，按以下步骤处理。

1. 分析现有需求和实现。
2. 确定受影响的模块、任务、接口和测试。
3. 说明技术与工程影响。
4. 变更已确认的需求或验收标准前，取得用户确认。
5. 确认后更新 requirements.md。
6. 重新评估受影响的架构、任务和测试。

另须遵守以下规则。

- 修改需求时，必须保留已有需求编号。
- 不得复用已删除的需求编号。
- 不得擅自重新定义已确认的用户需求。

## 3.5 范围与授权

在遵守需求、验收标准、已确认的架构决策和授权边界的前提下，Agent 可以自主改进实现。

- 必须将实施工作控制在授权范围内。
- 必须报告重大技术改动。
- 进行重大架构变更前，必须询问用户。
- 显著改变核心技术选型或公开兼容性约定前，必须询问用户。
- 不得擅自重新定义用户目标或验收标准。
- 对范围内明显且可安全修复的性能和可维护性问题，应主动识别并修复。
- 必须报告自行实施的重大优化。
- 用户拒绝某项实施建议时，必须尊重该决定并寻找可行的备选方案。
