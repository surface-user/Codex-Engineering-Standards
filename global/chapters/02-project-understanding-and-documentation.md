# 02. 项目理解与文档管理

## 2.1 了解项目

进入既有项目时，Agent 必须完成以下事项。

1. 检查所有适用的 AGENTS.md 指令。
2. 阅读项目级 AGENTS.md。
3. 了解项目概况和目录结构。
4. 阅读 `docs/` 下的相关文档。
5. 检查相关源码、配置、依赖、测试和 Git 状态。
6. 在进行重大改动前，掌握足够的项目背景。

相关文档可以包括以下内容。

- README.md
- docs/requirements.md
- docs/architecture.md
- docs/task.md
- docs/adr/
- docs/guides/

根据当前任务选择文档，避免读取无关材料。

## 2.2 核对文档与实现

文档描述已确认的项目事实，代码和配置体现实际实现。

- 必须对照实际代码与配置核实文档中的重要说法。
- 必须调查重大差异。
- 必须区分已确认的决策与尚未确认的实现变更。
- 必须向用户说明重大差异、成因、影响和可行方案。
- 在决定恢复文档所述设计或更新文档之前，必须取得用户确认。
- 不得将较新的实现直接视为已批准的工程决策。

若差异仅涉及普通实现细节，且不影响架构、外部行为或已记录的工程约束，可以自行处理。

改动已获用户明确授权时，在实现并验证成功后更新相关文档。

## 2.3 文档管理

区分当前有效的工程资料与开发历史。

- `docs/` 存放当前的项目需求、架构、任务、决策和开发指南。
- `dev/` 存放开发记录、历史报告和有价值的证据。
- `artifacts/` 按需存放生成的构建和测试产物。
- `.local/` 按需存放本地开发数据和临时环境。

文档管理须遵守以下规则。

- 创建 Markdown 文件前，必须检查已有文档。
- 必须优先更新已有文档，避免创建重复文件。
- 必须确保每份新增文档都有明确的工程用途。
- 不得将临时分析笔记或日常开发日志放入 `docs/`。
- 不得随意删除历史记录或有价值的测试证据。
- 必须使 README.md 与项目实际能力一致。
- 实际系统架构发生变化时，必须更新 architecture.md。
- 适当时应归档过时的历史资料。

仅当子目录确有额外约束时，才创建子目录级 AGENTS.md。

需要详细的文档操作流程时，查阅文档治理指南。
