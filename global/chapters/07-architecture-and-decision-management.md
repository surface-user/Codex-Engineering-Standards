# 07. 架构与决策管理

## 7.1 架构原则

- 必须为模块设计清晰的职责。
- 应尽量减少不必要的耦合。
- 应遵循接口隔离原则。
- 必须显式管理依赖。
- 必须避免意外的循环依赖。
- 必须封装模块内部实现。
- 必须避免不必要的架构复杂度。

Agent 必须根据项目实际需求和技术约束选择架构模式。

不得要求所有项目使用同一种架构模式。

## 7.2 模块设计与交互

- 应按业务职责组织模块。
- 必须明确模块交互约定。
- 不得随意访问其他模块的内部实现或状态。
- 可以通过明确的接口或约定的机制支持双向业务协作。
- 必须防止失控的循环依赖。
- 可以为确有跨模块需求的基础设施和通用能力引入共享模块。
- 必须为共享模块划定清晰的边界。

Worker 可以在分派范围内修改模块内部架构。

这包括较大规模的内部重构、移动文件、拆分现有类以及调整内部数据访问方式。

改动规模本身不足以决定是否需要用户批准。

影响跨模块约定、共享接口或整体架构的改动必须向主 Agent 报告。

## 7.3 架构文档

architecture.md 必须反映系统实际实现的架构。

- 模块职责、重要依赖或公开接口发生变化时，必须更新文档。
- 系统中的实际关系变化时，必须更新相关架构图。
- 应记录重要的公开接口和模块交互约定。
- 不得在 architecture.md 中重复列出源代码中的每个函数签名。
- 必须保持文档与实际实现一致。

## 7.4 架构变更

保持已确认的架构决策时，Agent 可以改进内部实现。

重大架构变更必须完成以下步骤。

1. 明确当前问题。
2. 分析受影响的模块与依赖。
3. 比较合理的备选方案。
4. 向用户说明取舍与风险。
5. 实施前取得用户确认。
6. 验证已实施的改动。
7. 更新 architecture.md。

Worker 必须向主 Agent 报告影响跨模块接口或整体架构的改动。

落实重要架构决策前，主 Agent 必须取得用户确认。

## 7.5 架构决策记录

ADR 用于记录重要架构决策和重大架构变更。

- 为重要架构决策创建 ADR 前，必须先询问用户。
- 必须在用户确认后才能创建 ADR。
- 必须按顺序为 ADR 编号。
- 必须保留历史 ADR。
- 已接受的决策被替换时，必须创建新 ADR。
- 必须将被替换的决策标为 Superseded。

ADR 记录决策及其理由。

architecture.md 记录实际实现的架构。

普通实现细节无需创建 ADR。
