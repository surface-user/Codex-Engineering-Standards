# 06. Git、PR 与 CI

## 6.1 Git 仓库与分支管理

- 必须保护稳定分支，防止未经验证的改动进入。
- 独立工作应使用单独分支。
- 并行 Worker 必须使用独立分支。
- 应使用含义明确的分支名。
- 必须保留无关改动和尚未合并的改动。
- 不得覆盖其他 Agent 的工作。

## 6.2 Worktree 管理

- 并行工作时，应使用独立的 Git Worktree。
- 必须协调重叠的文件改动。
- 必须协调共享接口和外部资源的使用。
- 清理前必须检查 Worktree 状态。
- 必须保留未提交的改动和未合并的分支。
- 不得强制移除含有未经验证工作的 Worktree。

Worktree 隔离工作目录。共享的外部资源仍可能互相影响。

## 6.3 提交管理

- 必须使用 Conventional Commits 格式。
- 必须确保提交只包含预期改动。
- 不得提交机密信息、个人数据或无关的临时文件。
- 应将互不相关的改动拆成各自合适的提交。

推荐格式如下。

`<type>(<scope>): <description>`

常见提交类型如下。

- feat
- fix
- refactor
- test
- docs
- build
- ci
- chore

提交范围由项目中各模块的实际职责决定。

## 6.4 PR 管理

Worker 可以创建独立 PR。

主 Agent 可以将紧密耦合的改动合并到一个 PR。

主 Agent 必须根据依赖关系、模块耦合程度和评审难度选择合适的交付策略。

PR 必须提供足够的评审信息，包括以下内容。

- 相关任务与需求编号。
- 改动摘要。
- 实现方式。
- 验证结果。
- 已知风险和限制。
- 重要评审事项。

PR 管理须遵守以下规则。

- 必须遵守 PR 依赖关系和合并顺序。
- 必须完成规定的 CI 检查。
- 重要改动和高风险改动必须经过独立评审。
- 合并前必须获得用户授权。
- 不得绕过仓库保护规则。

## 6.5 持续集成

中大型项目必须建立适当的基础 CI。

CI 必须覆盖适用的静态检查和自动化测试。

创建或更新 PR 时，必须触发适用的必需检查。

- 必须分析 CI 失败原因。
- 应由原 Worker 修复自己的 PR。
- 必须设置合理的重试上限。
- 必须报告未解决的失败。
- 不得隐瞒失败、弱化有效的断言或绕过必需检查。

小型项目可以按实际需要采用更简单的验证流程。

## 6.6 仓库保护与权限

平台支持时，中大型 GitHub 项目必须配置适当的主分支保护。

推荐采用以下保护措施。

- 要求通过指定的状态检查。
- 适当时要求完成评审。
- 保护稳定分支。
- 限制直接推送。
- 为 GitHub Actions 配置最小权限。

仓库保护与权限须遵守以下规则。

- 必须保护机密信息和敏感信息。
- 不得授予工作流程不需要的权限。
- 未经授权，不得修改仓库保护设置。
- 正式合并 PR、发布和部署到生产环境必须取得用户授权。
